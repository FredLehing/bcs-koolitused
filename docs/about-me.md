### PDFScanner — Saatelehtede automaatkontroll

**Periood:** Mai 2026 (3 päevaga valmis)
**Repo:** github.com/raintuur/pdfscanner
**Roll:** Ainuarendaja — kogu projekt on tehtud üksinda algusest lõpuni

**Mis probleem lahendatakse:**
Igal tööpäeval tuleb käsitsi võrrelda eelmise päeva NOOM-süsteemist eksporditud kütuse väljaminekute Exceli raportit füüsiliste tankimise saatelehtede PDF-piltidega. PDFScanner automatiseerib selle protsessi: loeb saatelehed AI abil, seob need NOOM andmetega ja esitab kasutajale selge ülevaate, millised saatelehed klapivad ja millised vajavad tähelepanu.

**Tehnoloogiad:**

| Kiht | Tehnoloogia |
|------|-------------|
| Backend | Java 21, Spring Boot, Spring AI, MapStruct, Flyway, Lombok, SpringDoc OpenAPI |
| AI mudel | Google Gemini (multimodal, JSON structured output) |
| Frontend | Vue.js 3, Vite, TypeScript, Pinia, Vue Router, Bootstrap 5, Phosphor Icons |
| Andmebaas | PostgreSQL (koos DB view'dega koondpäringute jaoks) |
| Infrastruktuur | Docker, Gradle |

**Maht ja keerukus:**
- Backend: 74 Java faili — 7 controller'it, 7 service'it (sh async worker), 18+ repository'd, 5+ MapStruct mapper'it, 12 persistence entity't
- Frontend: 25 Vue komponenti + 20 TypeScript faili, 12 route-taseme vaadet
- API: 15+ REST endpoint'i, OpenAPI dokumentatsioon
- Andmemudel: 12 tabelit + 3 DB view'd; mitmetasandilised seosed (noom_report → analysis_job → pdf_extraction → pdf_extraction_item → validation_report_item)
- Keerukam funktsioon: async analüüsi worker, mis käivitab kaks järjestikust AI-kõnet iga PDF-lehe kohta, tegeleb retry-loogika, osalise ebaõnnestumise ja transaktsiooniohutusega

**Olulised tehnilised lahendused:**
- `field_definition` konfiguratsioonitabel — kõik 16 võrreldavat välju (nimed, normaliseerimisreeglid, AI prompt-vihjed, asukohad vormil) on andmebaasis, mitte koodis; uue välja lisamine ei nõua koodimuutust
- Kahetasemeline AI-töövoog: 1. kõne tuvastab saatelehe numbri pildi kärpest (trükitud tekst), 2. kõne loeb käsikirjalised väljad täislehekülje pildilt, kasutades `field_definition` andmeid kontekstina
- Spring AI structured output (`.responseEntity(Class)`) — JSON vastus parsitakse otse Java DTO-ks, token usage loetakse samast `ChatResponse` objektist
- `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` muster: analüüsi worker käivitatakse pärast jobi loomise transaktsiooni commitit, HTTP request tagastab kohe `202 Accepted`
- PostgreSQL DB view'd (`noom_report_summary`, `validation_report`, `validation_report_field`) koondpäringute jaoks — frontend saab ühe päringuga kõik vajaliku info
- Frontend pollimine: vaade küsib analüüsi seisu iga 2 sekundi järel, kuvab failipõhise edenemisseinapaneeliga
- Validation staatuste hierarhia: field tase (`OK`/`REVIEW`/`ERROR`) → saateleht tase → analysis job tase; backend arvutab koondsatuse ise üle, ei usalda AI top-level vastust pimesi
- AI-kulude jälgimine: iga analüüsitöö tokenite arv ja maksumus salvestatakse `prompt_log` tabelisse, valideerimisraportis kuvatakse täpsuskulud

**Prompting arhitektuur (`field_definition` + system prompt):**

`field_definition` tabel ei ole pelgalt andmebaasi metaandmete tabel — see on runtime prompting infrastruktuur, mis süstitakse dünaamiliselt igasse AI-kõnesse:

| Veerg | Prompting tehnika |
|---|---|
| `form_label`, `form_location_hint` | Grounding — ankurdab AI täpsele vormiväljale ja asukohale pildil |
| `noom_value_example`, `pdf_value_examples` | Few-shot examples — näitab, kuidas väärtus saatelehel esineda võib |
| `normalization_instructions` | Chain-of-Thought — samm-sammulised juhised normaliseerimiseks (`"TK 1424" → "TK1424"`) |
| `prompt_hint` | Task decomposition — konkreetne ülesanne selle välja jaoks |

System promptides (`delivery-note-number.md`, `delivery-note-fields.md`) kasutatud tehnikad:

- **Role** — `"You are an expert document data extraction system"` — kalibreerib vastuste täpsuse
- **Grounding** — iga kõnega saadetakse kaasa NOOMi tegelik väärtus (`noomValue`), pildi asukohad ja näidised; mudel ei pea üldistama
- **Chain-of-Thought / Reasoning** — `reasoning` väli (1. kõne) ja `confidenceReason` väli (2. kõne) sunnivad AI-d mõttekäigu kirjalikult läbi tegema enne lõppvastust
- **Few-shot examples** — mõlemas promptis on konkreetne sisend-väljund näidis (sh normaliseerimise näited)
- **Task decomposition** — kahe eraldi kõne arhitektuur: esmalt saatelehe number (väike kärp, täpne formaadikontroll), siis alles 15 käsikirjalist välja (täisleht)
- **Output anchoring** — JSON schema + `"Return only valid JSON, no markdown"` + Spring AI structured output kolmekordne garantii parsitavale väljundile
- **Verification chain** — AI tagastab eraldi `pdfValue` (nagu saatelehel) ja `pdfNormalizedValue` (võrdluseks); backend kontrollib vastavuse ise üle, ei usalda AI otsust pimesi

**Kontekst:**
Projekt valmis RingIT poolt juhitud AI-arenduse koolituse raames (Vali IT programm, 4 päeva). PDFScanner valmis 3 päevaga (intensiivne töö, minimaalselt unetunde) ja sai demol RingIT eksperdilt kiita, et tulemus oli väga impressive.

**Maht ja keerukus:**
- Backend: 4 controller'it, 5 service'it (sh async worker + Prozorro client + dokumendikonverter), 8 persistence entity't
- Frontend: 3 vaadet — Prozorro ID sisestus (peamine UI), faili upload, debug-vaade
- API: REST endpoint'id hindamiseks, Prozorro integratsiooniks ja tugiandmeteks
- Andmemudel: 8 tabelit — procurement_type, quality_index, quality_criterion, tender, tender_document, evaluation, evaluation_criterion_result, prompt_log

**Olulised tehnilised lahendused:**
- Kaks paralleelset hindamistöövoogu: 1) `.md` faili otseupload (sünkroonne), 2) Prozorro hanke ID → dokumendi automaatne allalaadimine ja hindamine (asünkroonne)
- `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` muster: Prozorro töövoos hindamine käivitatakse taustal pärast transaktsiooni commitit, HTTP vastab kohe `201 Created`
- Dokumenditekstikonverter: PDFBox (PDF → tekst) + Apache POI (DOCX → tekst) — hankedokumendid tulevad Prozorrost PDF/DOCX formaadis
- Kolmekihiline AI system prompt: `procurement_type.system_prompt` (hanke kontekst) + `quality_index.system_prompt` (indeksi reeglid + roll) + `evaluation-rules.md` (fikseeritud JSON output formaat)
- `quality_criterion.prompt_hint` — alakriteeriumi hindamisjuhis süstitakse AI-le dünaamiliselt JSON array'na; uue kriteeriumi lisamine ei nõua koodimuutust
- Spring AI structured output (`.responseEntity(Class)`) — JSON vastus parsitakse otse Java DTO-ks
- Token kulude jälgimine: iga hindamiskõne tokenite arv ja maksumus (input / cached input / output) salvestatakse `prompt_log` tabelisse ja kuvatakse UI-s

**Prompting arhitektuur:**

Iga AI hindamiskõne system prompt on kolmekihiline: hanke tüübi kontekst → konkreetse indeksi roll ja skoorimisreeglid → fikseeritud JSON output skeemiga reeglid. User message sisaldab alakriteeriumide JSON array (koos `promptHint`-idega) + hankedokumendi täistekst. AI täidab nullväljad iga kriteeriumi kohta (`score`, `confidence`, `confidenceReason`, `finding`) ning tagastab ka top-level koondskoor ja summary.
