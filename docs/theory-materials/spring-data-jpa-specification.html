1. Probleem: miks @Query siin ei sobi

Seni kirjutasime kõik päringud nii: üks fikseeritud JPQL-tekst @Query annotatsioonis.

@Query("""
    select ts from TrainingSummary ts
    where (:categoryId = 0 or ts.categoryId = :categoryId)
    and ts.translationLanguageCode = :contentLang
    order by ts.training.isPromoted desc, ts.title""")

See töötab hästi, kui tingimuste arv on alati sama. Filtril „kõik“ on nipp :categoryId = 0 or ..., mis teeb tingimuse alati tõeseks.

Otsingus kirjutab kasutaja aga suvalise arvu sõnu:

Kasutaja sisestabMitu like-tingimust on vaja?
java1
java alg2
java alg kursus AI4

JPQL-i tekstis ei saa kirjutada „korda seda rida nii mitu korda, kui sõnu on“. Tekst on valmis enne, kui kasutaja midagi sisestab.

Analoogia – tellimisvorm vs Lego: @Query on nagu trükitud tellimisvorm, kus lahtrite arv on paberile ette trükitud. Specification on nagu Lego: sul on eraldi klotsid ja ühendad neid nii palju, kui parajasti vaja.

2. Mis on Specification?

Specification on üks tükk SQL-i WHERE tingimusest, kirjutatud Java koodina. See on väike funktsioon, mis saab kolm tööriista ja tagastab ühe tingimuse (Predicate):

(root, query, cb) -> cb.equal(root.get("categoryId"), categoryId)
//  │      │     │        │
//  │      │     │        └─ tulemus: tingimus "category_id = 3"
//  │      │     └─ cb = CriteriaBuilder: tööriistakast (equal, like, and, or, lower, exists...)
//  │      └─ query = päring ise (vaja nt alampäringu loomiseks)
//  └─ root = tabeli rida, millele tingimus käib (siin TrainingSummary)
Java (CriteriaBuilder)Mis SQL-ist tuleb
cb.equal(root.get("categoryId"), 3)category_id = 3
cb.like(cb.lower(root.get("title")), "%java%")lower(title) like '%java%'
cb.or(a, b)(a or b)
cb.and(a, b, c)(a and b and c)
cb.conjunction()1=1 ehk „alati tõene, ei filtreeri midagi“

Klotsid pannakse kokku meetodiga Specification.allOf(...) (kõik peavad kehtima, and). Et repository oskaks neid kasutada, lisatakse talle liides JpaSpecificationExecutor:

public interface TrainingSummaryRepository
        extends JpaRepository<TrainingSummary, Long>,
                JpaSpecificationExecutor<TrainingSummary> {   // ← annab meetodi findAll(spec, pageable)
}

Nagu findById puhul, kirjutab Spring meetodi findAll(specification, pageable) sinu eest valmis.

    4. Kus filtreerimine toimub – Javas või andmebaasis?
    


    Andmebaasis. See on kõige tähtsam mõte. Java ei loe kõiki koolitusi mällu ega sorteeri neid ise. Java ainult koostab SQL-lause, andmebaas teeb raske töö ja saadab tagasi ainult ühe lehe jagu ridu.
    


    Vajuta „Järgmine samm“ ja vaata, kuidas üks otsing liigub:
    


    
  
      
    
    1. Kasutaja kirjutab java alg ja vajutab „Otsi“. Vue
      GET /api/trainings?...&searchText=java%20alg
      2. 
    
    2. TrainingController võtab searchText query parameetrist ja kutsub teenust. Java
      3. 
    
    3. TrainingService paneb klotsid kokku: Specification.allOf(hasCategoryId, ..., containsAllWords). Andmeid pole veel kordagi loetud, ainult „retsept“ on valmis. Java
      4. 
    
    4. trainingSummaryRepository.findAll(spec, pageable) – Hibernate kutsub iga klotsi funktsiooni, saab tingimused ja kirjutab neist ühe SQL-lause. Java
      5. 
    
    5. PostgreSQL käivitab select ... where ... order by ... offset 0 rows fetch first 3 rows only. Filtreerimine, sorteerimine ja lehe väljalõikamine käivad siin. Andmebaas
      6. 
    
    6. Teine päring select count(*) ... where ... loeb kokku kõik sobivad read, et saada totalElements ja totalPages. Andmebaas
      7. 
    
    7. Javasse jõuavad tagasi ainult 3 rida ja üks arv. Service teeb neist DTO-d ja lisab rahastustüübid. Java
      8. 
    
    8. Vue kuvab kaardid ja leheküljenumbrid. Vue
      9. 
  
    
  
    
    
    
    
  
    

    


    Analoogia – raamatukogu: sa ei tassi kõiki 10 000 raamatut koju, et neid laual sorteerida. Annad raamatukoguhoidjale sedeli („Java raamatud, eesti keeles, esimesed 3“) ja saad kätte just need 3. Java kirjutab sedeli, andmebaas on raamatukoguhoidja.
    


    Seda näed ka päriselt: projektis on seadistatud P6Spy, nii et IntelliJ konsoolis on iga päringu järel näha täpne SQL koos väärtustega.
    



    5. Meie kood rida-realt
    


    5.1 Lihtne klots – kategooria
    

    public static Specification<TrainingSummary> hasCategoryId(Integer categoryId) {
    return (root, query, cb) -> categoryId == 0
            ? cb.conjunction()                                  // 0 = "kõik" → 1=1, ei filtreeri
            : cb.equal(root.get("categoryId"), categoryId);     // muidu category_id = ?
}
    

    NB: categoryId == 0 kontroll käib Javas, aga see ei filtreeri andmeid. See ainult otsustab, kas tingimus SQL-i lisatakse. Andmete filtreerimine jääb ikka andmebaasile.
    


    5.2 Klots alampäringuga – rahastustüüp
    

    public static Specification<TrainingSummary> hasFundingTypeId(Integer fundingTypeId) {
    return (root, query, cb) -> {
        if (fundingTypeId == 0) {
            return cb.conjunction();
        }
        Subquery<Integer> subquery = query.subquery(Integer.class);       // "select tft.id from ..."
        Root<TrainingFundingType> trainingFundingType = subquery.from(TrainingFundingType.class);
        subquery.select(trainingFundingType.get("id"))
                .where(cb.equal(trainingFundingType.get("training"), root.get("training")),
                       cb.equal(trainingFundingType.get("fundingType").get("id"), fundingTypeId));
        return cb.exists(subquery);                                        // "exists (select ...)"
    };
}
    

    Koolitusel võib olla mitu rahastustüüpi (many-to-many). exists küsib: „kas sellel koolitusel on vähemalt üks selline rahastus?“ Nii ei teki duplikaatridu ja leheküljestamine loeb koolitusi õigesti.
    


    5.3 Tsükliga klots – otsingusõnad
    

    public static Specification<TrainingSummary> containsAllWords(String searchText) {
    return (root, query, cb) -> {
        if (searchText == null || searchText.isBlank()) {
            return cb.conjunction();                                   // tühi otsing = kõik
        }
        List<Predicate> wordPredicates = new ArrayList<>();
        for (String word : searchText.trim().toLowerCase().split("\\s+")) {   // "Java  alg" → ["java", "alg"]
            String pattern = "%" + escapeLikeWildcards(word) + "%";           // "java" → "%java%"
            wordPredicates.add(cb.or(                                        // title VÕI kirjeldus
                    cb.like(cb.lower(root.get("title")), pattern, LIKE_ESCAPE_CHAR),
                    cb.like(cb.lower(root.get("shortDescription")), pattern, LIKE_ESCAPE_CHAR)));
        }
        return cb.and(wordPredicates.toArray(new Predicate[0]));          // kõik sõnad (AND)
    };
}
    

    Siin on Specificationi mõte: tavaline Java for-tsükkel lisab iga sõna jaoks ühe tingimuse. @Query tekstiga seda teha ei saaks.
    

    split("\\s+") tähendab „tükelda ühe või mitme järjestikuse tühiku kohalt“, nii et "java   alg" annab ikka kaks sõna.

    6. Lõks: % ja _ ehk escape'imine
    


    SQL-i like mustris on kaks erimärki (metamärki):
    

    
  
    MärkTähendus like-isNäide
    
  
    %ükskõik mis tekst (ka tühi)'%java%' sobib „Java algkursus“
    
  
    _täpselt üks suvaline märk'j_va' sobib „java“ ja „jova“
    

    


    Kui kasutaja kirjutab otsingusse %, tekib ilma kaitseta muster '%%%', mis sobib kõigega. Ootamatu tulemus! Lahendus on panna erimärgi ette \. See ütleb andmebaasile: „seda märki otsi tavalise tähena“.
    


    
  
    Proovi: mis muster SQL-i läheb?
    
  
  
    
    
    
      
    Ilma escape'ita
    
      
    
    
    
    
    
      
    Escape'iga (meie kood)
    
      
    
    
    
  
    

    


    // Kasutaja sisestatud % ja _ otsitakse sõna-sõnalt, mitte LIKE metamärkidena
private static String escapeLikeWildcards(String word) {
    return word.replace("\\", "\\\\")   // 1) kõigepealt \ ise, muidu topeltescape
            .replace("%", "\\%")
            .replace("_", "\\_");
}
// ja cb.like(..., pattern, '\\') ütleb andmebaasile, et \ on escape-märk

    8. Kokkuvõte
    

    
  
    MõisteLühidalt
    
  
    Specification<T>Üks WHERE tingimuse tükk Java koodina (funktsioon root, query, cb → Predicate).
    
  
    JpaSpecificationExecutor<T>Liides repositoryle, mis annab meetodi findAll(spec, pageable).
    
  
    CriteriaBuilder (cb)Tööriistakast tingimuste tegemiseks: equal, like, lower, and, or, exists.
    
  
    rootEntiteedi rida, mille väljadele viidatakse (root.get("title")).
    
  
    cb.conjunction()Alati tõene tingimus (1=1) – filter „kõik“.
    
  
    Specification.allOf(...)Paneb klotsid kokku and-iga.
    
  
    Sort + PageRequestJärjestus ja leheküljestamine; lähevad SQL-i order by ja offset/fetch osaks.
    
  
    Kus filtreeritakse?Andmebaasis. Java ainult koostab SQL-i.
    
  
    Escape% ja _ ees \, et kasutaja sisend ei muutuks metamärgiks.
